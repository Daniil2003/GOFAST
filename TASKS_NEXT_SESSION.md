# GoFast — задачи для следующей сессии ИИ-агента

Контекст: в проекте есть `gofast_eda.py`, `gofast_counts_test.py`, `build_pdf_reports.py`
и датасеты `datasets/{users_go.csv, rides_go.csv, subscriptions_go.csv}`.

Текущее решение качественно закрывает только вопрос «ultra ездит реже free» (число поездок)
и годовой доход тарифов. Три из четырёх гипотез постановки **не реализованы**.
Ниже — полный список того, что нужно исправить/добавить.

Ориентир фактов из данных (для самопроверки):
- users: 1 534 строки, колонки `user_id,name,age,city,subscription_type`; free 835, ultra 699.
- rides: 17 973 поездки, колонки `user_id,distance,duration,date`; период 2021-01-01 … 2021-12-30.
- subs: free = 50 ₽ старт + 8 ₽/мин; ultra = 0 ₽ старт + 6 ₽/мин + 199 ₽/мес.
- Минимальная длительность поездки ≈ 2,0 мин (поездок с `duration == 0.5` НЕТ).
- Средняя поездка ≈ 17,9 мин, ≈ 3 060 м.

Общие правила для всех новых скриптов: pandas/numpy/scipy/(statsmodels опционально),
сохранение результата в `output/`, кириллица в выводе, отсутствие захардкоженных
магических констант без обоснования.

## Задача 1. Гипотеза «подписчики тратят больше ВРЕМЕНИ на поездки» — реализовать

Сейчас в коде теста на `duration` нет. Есть только текст в `build_pdf_reports.py:209`
(«18,5 мин против 17,5 мин, разница стабильная») без статистики. Это недопустимо.

Что сделать:
1. Новый скрипт `gofast_time_test.py`.
2. Разделить две разные метрики и проверять их отдельно:
   - **время на одну поездку** — сравнение `duration` между группами;
   - **суммарное время за период** на пользователя — отдельная формулировка
     (иначе она почти дублирует число поездок, гипотеза №3 маскирует №1).
3. Тесты:
   - основной — Welch t-test на `duration` (величина непрерывная, распределение
     близко к нормальному), с CI разницы средних;
   - проверка нормальности (Shapiro/Харке-Бер, с оговоркой про объём выборки);
   - робастность — Mann-Whitney U как непараметрическая альтернатива.
4. **Обязательно учесть кластеризацию**: у одного пользователя много поездок,
   наблюдения не независимы. Варианты: агрегировать до средней длительности
   на пользователя, либо кластер-робастный тест / bootstrap по пользователям.
   Без этого p-value занижены.
5. Стратификация: отдельно по месяцам и городам (с поправкой Холма), как это
   сделано для counts.
6. Вывод: зафиксировать, подтверждается ли «ultra ездит дольше за поездку»
   значимо, и не путать с «больше суммарного времени».

## Задача 2. Гипотеза «расстояние одной поездки ≤ 3130 м у подписчиков» — реализовать и уточнить постановку

Сейчас по `distance` есть только описательные графики (`gofast_eda.py:130`) и
`speed_m_min` (`gofast_eda.py:61`). Теста против порога нет.

Что сделать:
1. Новый скрипт `gofast_distance_test.py`.
2. **Уточнить, что именно проверяем**, и посчитать обе версии:
   - «среднее расстояние за поездку не превышает 3130 м» → односторонний
     одновыборочный t-test `H0: μ ≤ 3130`, `H1: μ > 3130` (и отдельно для ultra, ultra+free);
   - «доля поездок длиннее 3130 м не превышает X %» → биномиальный тест на пропорцию
     с CI. Это самостоятельная и часто более честная формулировка.
3. Контроль качества: распределение `distance`, квантили, оценка хвоста
   (сколько поездок реально > 3130 м).
4. **Явно оговорить в выводе:** «оптимальность 3130 м с точки зрения износа» —
   это бизнес-предположение, а НЕ статистическая гипотеза. В данных нет индикаторов
   износа/поломок, поэтому проверить «оптимальность» нельзя. Проверяем только
   «не превышает / превышает ли порог».

## Задача 3. Гипотеза «помесячная выручка подписчиков выше» — доделать

Сейчас: помесячно считается только **число поездок** (`build_pdf_reports.py:211`),
а выручка — только годовой тотал (`gofast_eda.py:85`, `build_pdf_reports.py:242`).
Помесячной выручки нет.

Что сделать:
1. Построить **помесячный ряд выручки в рублях**:
   - free: `Σ (50 + 8 × duration)` по поездкам месяца;
   - ultra: `Σ (0 + 6 × duration)` по поездкам месяца **ПЛЮС абонплата**.
2. **Абонплата — ключевой фикс.** 199 ₽/мес — периодический платёж, его нельзя
   приписывать только месяцам с поездками. Корректно:
   `абонплата(месяц) = 199 × (число ultra, активных в этом месяце)`.
   Зафиксировать допущение, что все 699 ultra платят весь год (дат регистрации/оттока
   в `users_go.csv` нет), и показать, как вывод чувствителен к этому допущению.
3. Сравнивать **на пользователя (ARPU)**, а не абсолютные тоталы групп
   (группы разного размера: 835 vs 699).
4. Тест: 12 помесячных значений free vs ultra — это **зависимые (парные) наблюдения**,
   поэтому корректнее парный тест на 12 разностях (или смешанная модель month × tariff),
   а НЕ 12 независимых MWU. Для каждого месяца давать CI/значимость.
5. Вывод: обосновать/опровергнуть «помесячная выручка ultra выше free»
   с учётом абонплаты и допущений.

## Задача 4. Гипотеза «обновление серверов снизило обращения в техподдержку» — данных нет, надо зафиксировать блокер

В датасетах нет ни поля обращений в поддержку, ни даты обновления серверов.
Заготовка DiD в `gofast_counts_test.py:176-191` недописана (только печатает таблицу,
статистику не считает) и относится к релизу тарифов, а не к серверам.

Что сделать:
1. **Не фабриковать** результат. В отчёте/скрипте явно указать блокер:
   нужна отдельная таблица обращений (дата/период, число обращений) и дата деплоя T0.
2. Подготовить **каркас** анализа под DiD/ITS на будущее:
   - если появится контрольная группа (например, обращения по темам, не связанным
     с серверами) → Difference-in-Differences с проверкой предтрендов;
   - если контроля нет → interrupted time series / change-point, а не просто
     «до/после», иначе сезонность и общий тренд дадут ложное «снижение».
3. В коде оставить placeholder, который читает ожидаемый файл (например,
   `datasets/support_go.csv`) и **падает с понятной ошибкой**, если файла нет,
   а не тихо печатает пустой результат.
